# 条目字段规范（manifest.json）

> 这份规范回答一个问题：**别人拿到 index.json，能不能不读 README 就知道「能不能装、怎么装、我这一版 DSH 能不能用」。**
> 现在 1535 条里能机器回答这三个问题的不到 1%。这不是作者的问题——是字段没给出来。所以先定字段。

## 一、必填（现有校验已经在查）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 必须等于条目目录名 |
| `title` | string | 展示名 |
| `category` | string | 必须等于所在分类目录名 |
| `version` | string | 条目自身版本（不是 DSH 版本） |
| `summary` | string | 20~120 字 |
| `author` / `license` | string | — |
| `install` | string | 人读的安装说明（保留，别删） |
| `updatedAt` | string | `YYYY-MM-DD` |

## 二、`compat`：回答「我这一版 DSH 能不能用」

```json
"compat": {
  "dsh": ">=0.2.1-rc.2 <0.2.2",
  "os": ["win32", "darwin", "linux"],
  "arch": ["x64", "arm64"],
  "shell": "需要外壳实现启动动画契约",
  "notes": "非 Windows 下托盘通知不可用"
}
```

- `dsh`（**强烈建议必填**）：DSH 版本区间，写法同 npm semver：`^0.2.1`、`~0.2.1`、`>=0.2.1-rc.2 <0.2.2`、`*`。用户最常问的就是这句。
- `os`：字符串或数组，取值 `win32|darwin|linux`；不写 = 全平台。
- `arch`：同上，可选。
- `shell`：非插件类条目（启动动画、界面主题）常用于说明「要外壳支持什么契约」。
- `notes`：其它一句限制。

校验命令：`node tools/validate-compat.mjs`（形状与区间合法性）；列出某版本可用清单：`node tools/validate-compat.mjs 0.2.1-rc.2`。

## 三、`installSpec`：回答「怎么装」

`install` 是给人读的长句，机器解析不了。加一个可选的结构化字段，两者并存、不冲突：

```json
"installSpec": {
  "type": "npm",
  "pkg": "@nanmicoder/dsh-agent-teams",
  "version": "^0.1.26",
  "cmd": "dsh plugin --profile web add @nanmicoder/dsh-agent-teams@0.1.26"
}
```

`type` 取值与对应要求：

| type | 必填 | 含义 |
|---|---|---|
| `npm` | `pkg`，可选 `version`/`cmd` | 直接 `dsh plugin add <pkg>`；`cmd` 省略时由站点按平台拼 |
| `copy` | `src`、`target` | 把 `src/` 复制到某目录 |
| `patch` | `patch`（yaml 片段或路径） | 要往 `cordis.patch.yml` 加内容 |
| `manual` | 无 | 只能照 README 手工做（允许存在，但站点应标注「需手工」） |

`type:"manual"` 与「没有 installSpec」的区别：前者是**已确认无法自动化**，后者是**还没整理**。站点上应该分别显示成「手工」和「待补」，别混。

## 四、`verified`：回答「谁验过」

```json
"verified": { "by": "author", "at": "2026-10-22", "dsh": "0.2.1-rc.2" }
```

- `by`：`author`（作者自测）| `third-party`（第三方实测）| `none`。
- 与站点现有的「上架 ≠ 实测通过」一句话相比，这个字段能让用户按信任度筛选。

## 五、为什么要这么改（数据来自站点自身）

- 站点 1535 条里，`install` 字段含 npm 包名或可执行命令的只有 **12 条**，其中能直接复制执行的 **4 条**。
- 分类 856 条插件中，大量条目的可用性取决于 DSH 版本，但**没有一个字段**能被程序读到。
- `index.json` 目前只有 2 条（`generatedAt 2026-10-22`），与站点 1535 条不一致 —— 说明站点数据不是由本仓库构建链生成的。建议二选一：要么站点直读本仓库的 `index.json`，要么把真实数据源也放进仓库（只放 index.json 也行）。否则这份规范只能管到「新提交」，管不到存量。

## 六、迁移建议（存量 1535 条）

1. 先只加 `compat.dsh`：能用 `package.json` 的 `engines.dsh`/`peerDependencies` 自动填的自动填（本机脚本思路：从 `install`/`url` 抽出 npm 包名 → 查 registry → 读 `engines.dsh` 或 `peerDependencies["@deepseek-ai/dsh"]`）；抽不出的留空。
2. `installSpec.type` 先只判三类：`install` 里出现 `dsh plugin add` → `npm`；出现「复制/放入」→ `copy`；其它 → `manual`。
3. 站点展示层：条目卡片上直接标 `DSH ≥0.2.1-rc.2` / `仅 Windows` / `需手工安装`，这三个标就能砍掉大半无效点击。
